## Agent 是什么

既然是学习如何搭建 Agent 系统，那首先需要知道**Agent 是什么**。

在 Agent 出现之前，我们想要通过软件系统来完成一系列任务时，通常会选择 workflow 系统， workflow 系统提供预先定义好的任务步骤，用户只需要按照步骤执行即可。但因为任务都是预先定义好的，如果任务的步骤无法完全预先确定，那么 workflow 就无法满足需求。

```text
输入 -> 固定步骤 A -> 条件分支 -> 固定步骤 B -> 输出
```

Agent 则能解决无法预定任务步骤的问题，它**将大模型与工具相结合，形成一个完整的系统，能够自主感知环境、规划任务、调用工具、执行动作，并通过记忆不断改进，从而完成任务。**   所以任务不用预先定义好，而是可以动态调整。

换成一个简洁的公式就是：
```text
Agent = Model + Tool + Memory
```

## Agent 有哪些特性

对 Agent 是什么有了初步认识之后，接下来需要明确 **Agent 有哪些特性**。

1. **自主性（Autonomy）**
- 不依赖人一步步指挥，能在给定目标下自己决定“做什么、怎么做”。 （Model）

2. **感知能力（Perception）**
- 能从环境中获取信息：文本、文件、API 数据、数据库、网页、甚至图像/音频等。 （Tool）

3. **决策与规划（Reasoning & Planning）**
- 能理解目标、拆解任务、制定计划，并在执行中动态调整。 （Model）


4. **工具使用（Tool Use / Action）**
- 不只是“说话”，还能调用外部工具改变环境或获取信息。 （Tool）

5. **记忆与学习（Memory & Learning）**
- 有短期记忆（当前对话上下文）和长期记忆（历史经验、用户偏好、知识库）。 （Memory）

一个系统是不是 Agent，主要看它有没有上面这些特性。

拿 LLM 应用来说，它直接用自然语言向大模型发起调用，并给出答案，这个过程是短暂的，无法进行太多次的对话，并且只能回答问题， 无法进行任务处理。所以它**不是 Agent**。

```text
用户输入 -> Prompt -> 模型 -> 输出
```

而 RAG 是一种将大模型与向量检索相结合的系统，能够将外部知识库中的信息与大模型相结合，从而回答问题。它只是在模型调用前增加检索，把外部证据放入上下文，本身并不能处理任务。所以它也**不是 Agent**。但是Agent 可以包含 RAG，从而实现更复杂的任务处理。

```text
问题 -> 检索 -> 证据 -> Prompt -> 模型 -> 带证据的回答
```

## Agent 系统的构成

接下来看 Agent 系统的构成。


```text
用户输入
   ↓
[ 感知层 ] → 理解指令 & 环境
   ↓
[ 记忆层 ] → 短期 + 长期记忆
   ↓
[ 规划层 ] → 任务拆解 & 决策
   ↓
[ 行动层 ] → 调用工具 & 执行
   ↓
[ 反思层 ] → 校验 & 修正
   ↓
[ 安全层 ] → 约束 & 对齐
   ↓
输出结果 / 反馈用户
```

上一层的输出会作为下一层的输入，例如读到什么文件、工具返回什么、中间哪一步失败，都会改变下一步的行动。

这也带来新问题：死循环、越权、成本失控，以及失败后从哪里恢复，这些问题先有个概念，后续章节中会分别处理。

## Agent 和 Harness 的关系

除了 Agent 之外，我们还常听到 Harness 等概念，它们分别是什么？之间有什么关系呢？

Agent 是“干活的智能主体”（谁在决策、谁在推进任务）, 突出**目标驱动的执行主体**这个概念； 

Harness 是“套在它外面的可控运行系统”（怎么让它安全、稳定、可观测地干活），突出可控和可观测的**工程治理能力**。

业界常用等式：`Agent = Model + Harness`（这里的 Agent 是完整可运行系统，Model 是大脑，Harness 是身体和缰绳）。

例子： 

“帮我对比三家云厂商报价并出采购建议”，Agent 自己决定先搜谁、查哪些字段、怎么汇总。 

Harness 则负责确保 Agent 安全、稳定、可观测地干活，例如：
- 限制 Agent 的执行范围，防止越权
- 限制 Agent 的执行成本，防止成本失控
- 限制 Agent 的执行时间，防止执行时间过长
- 限制 Agent 的执行频率，防止执行频率过高
- 限制 Agent 的执行并发数，防止执行并发数过高

## Agent 工程和传统后端能力的异同点

对 Agent 的表现形式、特性、构成有了初步认识之后，接下来后续我们在搭建 Agent 系统时，需要考虑哪些传统后端能力需要保留，哪些需要新增加。

**Agent 工程保留了哪些传统后端能力**：

Agent 工程并没有抛弃传统软件工程。相反，模型的不确定性让原有工程能力更加重要。

**API 契约。** 模型输出可以变化，但 HTTP 接口、错误码和业务 Schema 必须稳定。上层系统不应该因为更换模型厂商就改请求格式。

**依赖注入。** 业务服务依赖 `ModelProvider` 接口，而不是直接依赖某个厂商 SDK。这样才能使用 Mock、切换 Provider，并让测试避开真实网络。

**测试、版本管理、权限边界和可回滚的发布。** 同样适用。换的是决策方式，不是工程方法。

**Agent 工程新增加了哪些能力**：

> 差别主要出在“模型参与决策”之后。

**可观测性从请求扩展到模型调用。** 普通后端会记录状态码和耗时。面向 Agent 的调用入口还应记录：

- 模型与 Provider
- Prompt ID 和版本
- 输入、输出 Token
- 延迟和估算成本
- 错误分类与重试次数
- `run_id` 或 Trace ID

**失败不再只有 HTTP 失败。** 模型调用可能出现四层失败：

1. 网络失败：连接错误、超时、断流。
2. 服务失败：限流、鉴权、5xx。
3. 协议失败：响应字段缺失、SSE 格式异常。
4. 内容失败：JSON 合法但不满足业务 Schema，或答案质量不合格。

不同失败需要不同策略，不能全部包装成一句“模型调用失败”。

## 这门课要搭建的平台

这个课程会基于 Agent 工程特性、构成与传统后端能力的异同点，搭建一个 Agent 平台， 我们将这个平台命名为 `agent-platform`。

```text
agent-platform/
├── apps/
│   ├── api/              # FastAPI：Gateway、工具、Agent 与评测接口
│   ├── web/              # Next.js：对话、任务、审批与运营控制台
│   └── worker/           # 后续长任务执行进程
├── packages/
│   ├── evals/            # Golden Tasks、Benchmark 与评测结果
│   └── shared/           # 跨应用共享协议
├── infra/                # 数据库、缓存和部署配置
└── docs/                 # 架构、基线、Runbook 与复盘
```

后续的章节中我们逐步完善这个平台，使其具备 Agent 工程的特性和能力。


在第一章中，我们会先创建 `apps/api`、`apps/web` 和 `packages/evals` 的一部分， 先完善模型入口请求，并完成一个可测试的 FastAPI 后端，让平台先拥有一个稳定的 HTTP 基线。

具体的课程目标是： 

- 一个 OpenAI-compatible FastAPI 模型服务
- 一个真实 Provider 与一个 Mock Provider
- 普通调用和可取消的 Streaming 调用
- Prompt 模板与版本字段
- Structured Output 校验与失败处理
- 基础模型路由、重试与 fallback
- Token、Cost、Latency 和 Trace ID 记录
- 一份可以复现的模型调用基线报告

后续的章节中我们才会实现 Function Calling、MCP、Agent Loop、RAG 和 Multi-Agent。
